# 会话工作流（开场 → 执行 → 验证 → 收尾）

用户 2026-10-27 裁定。适用于用 Athena 管理 sprint、多写者协作的会话。项目自己的命令与环境细节写在项目 rules，本文件只放通用流程。

## 1. 开场（用户说「开工 / 按会话流程」即执行）

读：交接文档最新一段（`.ai_state/HANDOFF.md`）、`queue.md`、`issues.md`、sprint 总表（如有）、`athena status`（多仓项目每个账本都读）；各工作仓库的 `git status` / worktree / 分支；冒烟要用的端口。

先用表格和用户核对 5 类，再给计划：

| # | 类 | 内容 |
|---|---|---|
| 1 | 已完成 | 上个会话 ship 的 sprint 与要点 |
| 2 | 排队中 | 按 queue 顺序，标依赖、能否并行 |
| 3 | 延后 | deferred 项与等用户裁定的事项 |
| 4 | 预警和风险 | 开放债务、已知坑、环境注意点 |
| 5 | 待确认 | 需用户拍板的问题，每条附推荐 |

然后给本会话 sprint 清单：每刀写路径、仓、写者、能否并行、预估，排好执行顺序。

- 预警和债务排最前，避免越积越多导致后续 sprint 偏移；延迟或堵塞的项按进度判断是否加入。
- 每个工作仓库每会话排一刀依赖升级，latest 以包管理器官方查询（如 `npm view <pkg> dist-tags`）为证。
- 开刀前核实 roadmap 条目是否已在别处做完，做完的直接补标 done。
- 用户说「按推荐」即执行；可逆的选择先按最优推荐做，事后列出请用户确认。

## 2. 写者

- 同时 ≤3 个写者。复杂 / 跨系统 / 安全 → 主力模型写者；中等 → 外部写者（如 codex）；只读调研 → 调研写者。每刀 review 用与写者不同家族的 reviewer；最强模型只在会话末做一次整体 review。
- 简报必写：不过度设计、不做防御性编程（对齐主流 agent 工具行为，边界只设在用户输入与跨进程 / 跨租户）；不许删注释或压行挤行数棘轮（超了拆文件）；迁移号预分配；项目代码约定；不执行 athena、不碰 `.ai_state/`；写者每完成一个 AC 就 commit，中断不丢。
- 遇到不熟悉的功能：先检索 GitHub 近 2 年维护活跃、许可证明确的同类开源项目，比较思路、依赖、已知问题，借鉴经过验证的设计，不直接复制不兼容或来源不明的代码。
- UI：Avoid unnecessary secondary labels and descriptions. Let the layout do the explaining（不加副标题、说明段、空态长文案；靠分组、对齐、图标、悬停提示）。
- 写者撞轮次上限或断网 → `SendMessage` 让它续做；会话重启后旧子 agent 不可续，先看其 worktree 的 `git log` / `status`，已提交的照常合入。
- 外部写者用后台命令跟踪完成（不用 nohup）；需要联网 / 跨仓写入时显式开对应权限；它不能提交或建 worktree 时由主 agent 代办。新建 worktree 先装依赖。
- 代写者提交前先看 `git diff --stat` 逐条对照简报 / review 发现；提交信息按实际 diff 写，不照抄写者报告（10-27：返工报告称已修三条，diff 里只有一条）。

## 3. 验证分层

| 时机 | 跑什么 | 耗时 |
|---|---|---|
| 每刀 | 本刀功能对应的测试目录 + 守卫类快检 + typecheck | 1–3 分钟 |
| 会话末一次 | 根全量测试 + lint + build，最终整体 review 之前 | 约 10 分钟 |

- 守卫快检每刀都带：行数棘轮、导出边界、组件规范等最常见的问题都是它挡下来的；跨刀问题在会话末全量统一修。
- design 的 AC 写本刀命令，不写「根全量」。
- 证据命令必须是单条 `athena run --covers ACn -- <cmd>`；`sh -c "a && b"` 包装判为不可证明。e2e / capture 记为不可证明，但要跑。
- 高负载偶发失败：单跑该文件确认后重跑，不改测试。
- 冒烟 / e2e 前先确认端口在听、健康检查返回 200。

## 4. 合入与 review

- 合入前先 `athena sprint resume <slug>`；`athena writer collect` 非快进时 `git merge --no-ff <branch>` 再 collect。
- `athena run` 进行中不切换活跃 sprint（证据按活跃 sprint 归属）。
- review packet 绑定源码树：packet 发出后到 accept 前，主树不提交任何东西（含 review 修复、别刀合入）；工作区新增的未跟踪文件也算进树，要写先放树外。先 accept 落盘（reviewer 原文逐字），再改代码、再 prepare 下一轮。
- 多刀批量：先合完 → 各刀在同一棵树上补证据并 prepare → reviewer 并行 → 逐个 accept → 再动树。等 review 时先把下一批写者派出去。
- 冲突以主线为准、重新应用分支意图；行数基线冲突取实测值（只降不升，补回注释的除外）。
- 跨仓接口升版后，消费方立即同步合同；请求体新字段要有能力位，消费方按位下发，避免连旧版本被拒。
- 每刀 ship 后给用户一行进度：`✅ <slug>：要点`。

## 5. 收尾

1. 根全量 + lint + build（每个工作仓库），修跨刀问题。
2. 最终整体 review（含依赖是否最新 + 已知漏洞），修 P0 / P1，其余记债后 ship。
3. 更新交接文档（顶部新段，旧段归档）、sprint 总表、`issues.md`；`athena tidy --dry-run` 后再 tidy；`.ai_state` 减负。
4. 各工作仓库：清缓存、废弃测试文件、过期与废弃代码；合并代码、删已合并的 worktree 与分支。
5. 推送（`.ai_state` 记账随代码同一提交）。
