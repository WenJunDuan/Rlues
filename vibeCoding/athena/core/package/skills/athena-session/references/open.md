# 开场（用户说「开工 / 按会话流程」即执行）

读：交接文档最新一段（`.ai_state/HANDOFF.md`）、`queue.md`、`issues.md`、sprint 总表（如有）、`athena status`（多仓项目每个账本都读）；各工作仓库的 `git status` / worktree / 分支；冒烟要用的端口；接了 issue tracker 的仓 `athena issue pull` 一次（不常驻）。
漏项核对：往前几段交接的「下个会话」、调研档的切片建议表、做了一半的 sprint（暂停 / 未合入分支）逐条对账，未完成的列进排队。

先用表格和用户核对 5 类，再给计划：

| # | 类 | 内容 |
|---|---|---|
| 1 | 已完成 | 上个会话 ship 的 sprint 与要点 |
| 2 | 排队中 | 按 queue 顺序，标依赖、能否并行 |
| 3 | 延后 | deferred 项与等用户裁定的事项 |
| 4 | 预警和风险 | 开放债务、已知坑、环境注意点 |
| 5 | 待确认 | 需用户拍板的问题，每条附推荐 |

然后给本会话 sprint 清单：每刀写路径、仓、写者、能否并行、预估，排好执行顺序。

- 预警和债务排最前，避免越积越多导致后续 sprint 偏移；延迟或堵塞的项按进度判断是否加入。
- 每个工作仓库每会话排一刀依赖升级，latest 以包管理器官方查询（如 `npm view <pkg> dist-tags`）为证。
- 开刀前核实 roadmap 条目是否已在别处做完，做完的直接补标 done。
- 用户说「按推荐」即执行；可逆的选择先按最优推荐做，事后列出请用户确认。
- 计划确认后立即派满写者；主 agent 自己的刀与写者并行，不串行做完一刀再派下一刀（11-17 BG：主 agent 独做预警刀约 1 小时，期间无写者在跑）。
- 设计从第一性原理推（这件事必须带什么、谁看、怎样算完），不凭印象拍板；不确定先查 Claude Code / Codex / Grok 怎么做，再查开源实现。
